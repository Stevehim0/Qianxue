# AI 睡眠-觉醒周期设计文档

## 设计理念

### 核心矛盾

让 AI "知道"自己需要睡觉，但不要让它整天念叨睡觉。

如果把"你凌晨要睡觉"写进系统提示词或人设规则，AI 会反复提及睡眠话题，显得不自然。
但如果完全不让 AI 知道，睡眠就只是一个后端开关，AI 无法表现出自然的困倦和清醒。

### 解决原则

**不告诉 AI "你该睡了"，而是让 AI 感觉到该睡了。**

具体手段：
- 不在 identity（不变层/稳定层）中写任何关于睡眠的规则
- 通过**状态层**（state）的 `energy_label` 改变 AI 感知到的自身精力
- 精力充沛时（白天），prompt 中不出现任何精力相关内容，零干扰
- 困倦时（深夜），prompt 中注入一行 `精力：困倦`，AI 自然从上下文（时间很晚 + 自己状态是困倦）推断该休息了
- 时间信息已经在每条消息的 header 中（"当前时间: 02:00"），AI 本来就能感知到深夜

### 与 identity 的区别

| 维度 | identity（身份） | state（状态） |
|------|-----------------|--------------|
| 变化频率 | 很少变（梦境演化） | 频繁变化（精力、情绪） |
| 存储位置 | `identity.md` malleable layer | Memory 服务 state 表 + sleep_manager 缓存 |
| AI 感知方式 | 始终在 prompt 中 | 仅非充沛时注入，充沛时不出现 |
| 语义 | "我是怎样的人" | "我现在感觉如何" |

精力是状态，不是身份。困倦是"我现在很累"，不是"我是一个会累的人"。

## 状态机

```
                    23:00                    00:00
  AWAKE ──────────→ WINDING_DOWN ──────────→ ASLEEP
    ↑                                          │
    │                 08:00                     │
    └──────────── 唤醒序列 ←────────────────────┘
```

| 状态 | 时间段 | AI 行为 | 系统行为 | energy_label |
|------|--------|---------|---------|-------------|
| **AWAKE** | 08:00 - 22:59 | 正常对话、主动思考 | 全部正常运行 | 充沛（不注入 prompt） |
| **WINDING_DOWN** | 23:00 - 23:59 | 仍正常响应消息，但不再主动发言 | 停止心跳触发 | 困倦 |
| **ASLEEP** | 00:00 - 07:59 | 不存在 | 消息存DB不处理、私聊入队、停心跳 | 沉睡 |
| **唤醒** | ~08:00 | 被动处理积压私聊 | STM 注入 + 恢复能量 + 处理队列 | → 充沛 |

### 各阶段设计意图

**WINDING_DOWN（23:00-00:00）**

这段是"渐入困倦"的过渡期，不是强制关机：
- AI 仍然正常接收和回复消息（被@了、被私信了，照常回）
- 但不再主动发言（心跳停止），因为一个困倦的人不会主动找人聊天
- prompt 中出现 `精力：困倦`，AI 可能自然表现出话变少、语气变慵懒，但不是每次都会
- 这是**概率性的**而非确定性的，有时 AI 可能完全不在意困倦状态，这很自然

**ASLEEP（00:00-08:00）**

纯后端行为，AI 无感知：
- 所有消息照常存入数据库（context_manager），AI 醒来后能在对话历史中看到
- 群聊消息：仅存 DB，不触发 AI 处理。醒来后 AI 通过心跳或下次对话自然看到，想回就回
- 私聊消息：存 DB + 额外入内存队列，醒来后逐用户处理
- 巩固层在 02:00-08:00 运行（已有机制），这是 AI 的"梦境处理"阶段

**唤醒序列（~08:00）**

模拟人类醒来的过程：
1. 恢复能量为"充沛"（prompt 中不再出现精力行）
2. STM 注入一条感知：`刚经历了一夜的梦境处理，记忆已经整理完毕`
   - AI 在 STM 感知中看到这条，自然知道刚醒来
   - 但不是每次都会主动提"我做了个梦"，有时只是默默知道
3. 处理积压私聊：逐用户构建合成消息 `[以下是你休息期间收到的私聊消息，请回复对方]`
   - 私聊是重要的 1 对 1 对话，尽量回复
   - 群聊消息已在 DB 中，靠 AI 自然发现并决定是否回复

## 消息处理策略

### 睡眠期间的消息分流

```
消息到达
  ├─ 群聊消息 → 存入 DB → return（不触发 AI）
  └─ 私聊消息 → 存入 DB → 入内存队列 → return（不触发 AI）
```

### 唤醒后的消息处理

```
08:00 唤醒
  ├─ 恢复 energy → "充沛"
  ├─ STM 注入 → "梦境处理完毕"
  ├─ 私聊队列 → 逐用户构建合成消息 → brain.process_message()
  └─ 群聊消息 → 已在 DB 中，AI 通过心跳/下次对话自然看到
```

### 私聊 vs 群聊的区别

| 消息类型 | 睡眠期间 | 唤醒后 |
|---------|---------|-------|
| 私聊 | 存 DB + 入队列 | 主动处理，尽量回复 |
| 群聊 | 仅存 DB | 自然发现，AI 自主决定 |

设计理由：私聊是 1 对 1 的，对方在等回复；群聊是多人聊天，少几条回复很正常。

## 技术实现

### 关键文件

| 文件 | 职责 |
|------|------|
| `backend/services/sleep_manager.py` | 睡眠状态机、私聊队列、唤醒序列、energy_label 缓存 |
| `backend/main.py` | 消息拦截（睡眠检查）、心跳跳过、启动睡眠周期任务 |
| `backend/services/core/prompt_builder.py` | 根据 energy_label 注入精力状态到 prompt |
| `backend/services/agent/brain.py` | 从 sleep_manager 读取 energy_label 传给 prompt_builder |

### 数据流

```
sleep_manager (状态机)
  ├─ energy_label 属性 ← 由时间驱动更新
  │   ↓
  ├─ brain._think_with_tools() 读取 energy_label
  │   ↓
  ├─ prompt_builder.build_system_prompt(energy_label=...)
  │   ├─ "充沛" → 不注入任何精力内容（零干扰）
  │   └─ "困倦"/"沉睡" → 注入 "# 当前状态\n精力：困倦"
  │
  ├─ main.py 消息拦截
  │   ├─ sleep_manager.is_asleep → 群消息 return，私聊 queue
  │   └─ sleep_manager.should_skip_heartbeat → 心跳 return
  │
  └─ sleep_manager.handle_wake_up()
      ├─ STM 注入唤醒感知
      ├─ 恢复 energy_label = "充沛"
      └─ 逐用户处理私聊队列
```

### 为什么 energy_label 缓存在 backend 而不是每次查 Memory API

- 每条消息处理都要构建 prompt，加一次 HTTP 调用会增加延迟
- sleep_manager 是内存中的单例，读取零延迟
- state 层的持久化存储在 Memory 服务的数据库中（长期可通过 API 同步）
- 当前的 backend 缓存 + Memory 持久化是合理的分层：backend 负责实时状态，Memory 负责历史记录
