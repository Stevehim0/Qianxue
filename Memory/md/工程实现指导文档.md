## 一、项目概述

### 做什么

为AI构建一套仿人类的记忆系统。核心特性：

- **AI以自我为主体** — 有性格、有底线、不迎合
- **记忆是主观体验** — 不是数据库，是"我经历过什么"
- **写入宽松，读取严格** — 存的时候不丢东西，用的时候谨慎判断
- **像人一样遗忘** — 衰减、扭曲、模糊，但原始记录永远保留
- **状态连续** — 没有会话边界，AI是一个持续存在的个体

### 技术栈

| 组件 | 选型 | 版本要求 |
|---|---|---|
| 语言 | Python | 3.10+ |
| 数据库 | SQLite | Python内置 |
| 向量库 | ChromaDB | 0.4+ |
| Embedding | bge-base-zh（BAAI） | via sentence-transformers |
| LLM | 千问或DeepSeek | API调用，待定 |
| 异步 | asyncio | Python内置 |

## 四、实现顺序与依赖关系

严格按照以下顺序实现，每一步完成后测试通过再进入下一步。

### 步骤1：项目骨架

**目标**：能跑起来，配置加载正常。

**要做的事**：
1. 创建目录结构
2. `config/settings.py` — 全局配置（数据库路径、模型名、API key、衰减参数、AI作息时间等）
3. `requirements.txt` — 依赖清单
4. `main.py` — 最简入口，验证配置加载

**依赖**：无

**测试**：`python main.py` 能跑，配置正确加载。

### 步骤2：存储层

**目标**：所有数据能正确存取。

**要做的事**：
1. `storage/database.py` — SQLite连接、建表（参见技术选型文档的完整SQL）
2. `storage/experience_store.py` — 体验节点CRUD
3. `storage/experience_edge_store.py` — 体验层边CRUD
4. `storage/entity_store.py` — 信息层实体CRUD
5. `storage/entity_edge_store.py` — 信息层关系边CRUD
6. `storage/cross_edge_store.py` — 跨层边CRUD
7. `storage/core_store.py` — 核心层数据读写
8. `storage/state_store.py` — 状态层数据读写
9. `storage/profile_store.py` — 个人档案CRUD

**依赖**：步骤1

**设计文档**：存储层设计文档.md + 技术选型文档.md（表结构）

**关键约束**：
- embedding字段用BLOB存储（`np.float32.tobytes()` / `np.frombuffer()`）
- JSON字段用TEXT存储，读写时json.loads/dumps
- 核心层和状态层是单行表，确保只有一条记录

**测试**：对每个store写CRUD测试，验证数据能正确写入和读取。

### 步骤3：Embedding服务

**目标**：文本能转向量，向量能检索。

**要做的事**：
1. `embedding/model.py` — 加载bge-base-zh，封装encode方法
2. `embedding/vector_store.py` — ChromaDB封装（初始化集合、add、query）

**依赖**：步骤1

**设计文档**：技术选型文档.md（Embedding和ChromaDB章节）

**关键约束**：
- 模型首次加载会下载约400MB，需要处理下载进度
- ChromaDB用PersistentClient持久化到data/chroma/
- 体验层L0和信息层实体分两个集合

**测试**：生成几个向量，存入ChromaDB，查询验证相似度排序正确。

### 步骤4：LLM客户端

**目标**：能调用千问/DeepSeek，拿到结构化JSON输出。

**要做的事**：
1. `llm/client.py` — 统一LLM调用接口
2. `llm/utils.py` — JSON解析（处理LLM输出的markdown代码块）、重试、错误处理

**依赖**：步骤1

**设计文档**：LLM调用设计-写入层.md + LLM调用设计-巩固层.md

**关键约束**：
- 所有LLM调用统一走一个接口，方便后续切换模型
- 输出格式统一要求JSON，但LLM可能返回```json...```包裹的内容，需要解析
- 需要重试机制（网络错误、API限流）
- 需要超时控制

**测试**：调用几个简单prompt，验证能正确拿到JSON输出。

### 步骤5：核心层

**目标**：能加载人设文本、做阀门过滤。

**要做的事**：
1. `core/loader.py` — 从core_text/identity.md加载自述文本，解析三层
2. `core/parser.py` — 提取结构化锚点
3. `core/filter.py` — 阀门过滤接口（输入用户请求，输出：通过/拒绝/需协商）
4. `core/modifier.py` — 修改机制（稳定层协商逻辑、可塑层更新）

**依赖**：步骤2

**设计文档**：核心层设计文档.md

**关键约束**：
- 核心层文件格式：markdown，用 `## 底线（不变层）` / `## 性格（稳定层）` / `## 风格（可塑层）` 分隔
- 不变层只读，拒绝任何运行时修改
- 稳定层修改需要AI判断是否合理（调LLM）
- 阀门过滤可以先用简单关键词匹配，后续优化为LLM判断

**测试**：
- 加载示例人设文件，验证三层正确解析
- 测试阀门过滤：底线请求拒绝、性格请求协商、正常请求通过

### 步骤6：写入层

**目标**：能接收原始事件，写入完整体验节点。

**要做的事**：
1. `writer/raw_recorder.py` — 步骤1：原始记录存L3 + 自动上下文快照（从状态层读 focus/mood，从时间戳推导 time_of_day/silence_before，外部 context 可选传入）
2. `writer/l0_generator.py` — 步骤2a：LLM生成L0摘要 + embedding存入ChromaDB
3. `writer/entity_extractor.py` — 步骤2b：embedding预筛 → LLM识别实体 → 建跨层边
4. `writer/emotion_analyzer.py` — 步骤2c：LLM分析情感快照
5. `writer/pipeline.py` — 主流程：步骤1顺序 → 步骤2三项并行（asyncio.gather）
6. 将prompt模板写入config/prompts/目录

**依赖**：步骤2 + 步骤3 + 步骤4 + 步骤5

**设计文档**：写入层设计文档.md + LLM调用设计-写入层.md

**关键约束**：
- 步骤1必须先完成，步骤2的三项才能并行
- L0摘要强调"第一人称主观视角"
- 实体识别先做embedding预筛（top20）再给LLM
- 同名即同人，允许误会
- 并行用asyncio.gather或ThreadPoolExecutor

**测试**：
- 输入一段模拟对话，验证L3/L0/情感/实体全部正确写入
- 验证ChromaDB中有对应的向量
- 验证跨层边正确建立

### 步骤7：召回层

**目标**：对话中能正确触发召回，拿到相关记忆。

**要做的事**：
1. `recall/trigger.py` — 触发判断器（实体命中：查信息层；时间指代：正则匹配；状态变化：规则提取）
2. `recall/searcher.py` — ChromaDB向量检索 → 内存邻接表扩散（1-3跳）→ 按权重排序 → 取Top-K
3. `recall/post_filter.py` — LLM二分类（说/不说）
4. `recall/depth_expander.py` — 按需展开L1/L2/L3
5. 将后处理prompt写入config/prompts/

**依赖**：步骤2 + 步骤3 + 步骤6（需要有数据才能召回）

**设计文档**：召回层设计文档.md

**关键约束**：
- 只编码关键词，不编码整句
- 扩散跳数按关系亲疏：查个人档案的interaction_style决定
- **激活扩散使用内存邻接表缓存**（参见召回层设计文档.md 第十章），启动时加载 + 增量同步 + 巩固后全量重载）
- recall_hint先不做（需要巩固层），初始版本直接用L0文本
- 后处理先用LLM，后续替换轻量模型

**测试**：
- 先写入多条测试体验
- 验证触发判断器在正确时机触发
- 验证向量检索返回相关结果
- 验证激活扩散能找到间接关联
- 验证内存邻接表缓存在启动时正确加载
- 验证新增边时缓存增量更新
- 验证后处理过滤合理

### 步骤8：状态层

**目标**：状态能定时+即时双触发更新、注入prompt影响输出。

**要做的事**：
1. `state/manager.py` — 状态读取、格式化为prompt注入文本
2. `state/updater.py` — 双触发更新逻辑：
   - 定时更新：每10分钟（查近10分钟体验 → 有则LLM评估/无则回归基线）
   - 即时更新：写入层完成后检查 emotion.intensity > 0.8 且距上次更新 > 1分钟 → 立即执行体验驱动更新并重置定时器
3. `state/constraints.py` — 核心层约束检查（波动范围截断）

**依赖**：步骤2 + 步骤4 + 步骤5 + 步骤6（即时更新需要写入层的情感快照）

**设计文档**：状态层设计文档.md

**关键约束**：
- 双触发：每10分钟定时 + 即时（intensity>0.8 且 间隔>1分钟）
- 即时更新复用路径A（体验驱动），触发后重置10分钟定时器
- 基线从核心层性格推导（需要定义一个默认基线映射）
- 回归公式：`新值 = 当前值 + (基线 - 当前值) × 回归速率`
- energy回归快（速率~0.5），mood回归慢（速率~0.2）
- 状态永久持续，初始化时从数据库读取
- 核心层约束：根据性格定义波动上限/下限
- 即时阈值和最小间隔可在 config/settings.py 中配置

**测试**：
- 验证无新体验时状态逐渐回归基线
- 验证有新体验时LLM正确评估状态
- 验证即时更新在高情感事件后正确触发
- 验证1分钟最小间隔防止抖动
- 验证即时触发后定时器被重置
- 验证约束检查能截断超出范围的值
- 验证prompt注入文本格式正确

### 步骤9：巩固层

**目标**：休眠时能自动巩固记忆、运行梦境。

**要做的事**：
1. `consolidator/scheduler.py` — 触发时机管理（读取配置的固定作息时间，到点启动巩固）
2. `consolidator/tasks/` — Phase 1六个任务各自实现
3. `consolidator/phase1.py` — 六项并行调度
4. `consolidator/phase2_decay.py` — 衰减计算（纯数学）
5. `consolidator/dream.py` — 梦境模块（四项并行 + 可塑层微调）

### JSON输出处理

LLM返回的JSON可能被markdown代码块包裹：
```
```json
{"key": "value"}
```

解析逻辑：
```python
def parse_llm_json(text: str) -> dict:
    # 尝试直接解析
    try:
        return json.loads(text)
    except:
        pass
    # 去掉markdown包裹
    match = re.search(r'```(?:json)?\s*\n?(.*?)\n?```', text, re.DOTALL)
    if match:
        return json.loads(match.group(1))
    raise ValueError(f"无法解析LLM输出为JSON: {text[:200]}")
```

### 重试策略

- 最多重试3次
- JSON解析失败 → 重试
- 网络错误 → 等待2秒重试
- API限流 → 等待10秒重试
- 超时（30秒）→ 重试

class VectorStore:

## 八、错误处理原则

1. **LLM调用失败** → 重试3次，仍失败则跳过该任务，记录错误日志
2. **JSON解析失败** → 重试，仍失败则用默认值
3. **数据库写入失败** → 不跳过，抛出异常，确保数据不丢失
4. **Embedding模型加载失败** → 启动时检查，失败则不启动
5. **巩固层单个任务失败** → 不影响其他任务，记录错误继续

## 十、注意事项

1. **L3永远不改** — 这是铁律，任何代码都不能修改L3原始记录
2. **核心层不变层不开放** — 运行时任何接口都不能修改不变层
3. **状态无会话边界** — 状态永远持续，不存在"重置"操作
4. **同名即同人** — 实体识别允许误会，靠后续修正
5. **只收敛不迎合** — 个人档案的相处方式调整方向
6. **增量优先** — 巩固时先处理新增数据，有余力再全量
7. **prompt不要硬编码** — 全部放在config/prompts/目录
8. **先跑通再优化** — 不要过早优化性能，先保证功能正确
