# 记忆系统 - 召回层设计文档

> 讨论日期：2026-03-30
> 状态：召回层讨论完成

---

## 一、职责

召回层的核心职责是**在合适的时机，以自然的方式，将相关记忆融入AI的回复**。不是简单的关键词搜索，而是模拟人类"想起什么"的过程。

---

## 二、核心原则

- **不每次都召回** — 大部分对话直接回复，只有特定信号触发召回
- **关系驱动** — 对不同亲疏关系的人，召回深度不同
- **以自我为主体** — AI不迎合对方，保持自己的性格和判断
- **自然使用记忆** — 召回结果经后处理，像人类一样自然地提起，不是机械引用
- **编码关键词而非整句** — 避免embedding模型稀释关键信息

---

## 三、触发判断

不是每句话都触发召回，需要一个轻量的触发判断器。

### 触发信号（按成本从低到高）

**1. 实体命中（零成本）**

对话文本中出现信息层已有的实体名字 → 直接触发。

```
"张三最近怎么样" → 命中 "张三" → 触发召回
```

**2. 时间指代词（低成本，正则匹配）**

检测关键词："上次"、"之前"、"那天"、"还记得"

```
"上次我们去的那家店" → 命中 "上次" → 触发召回
```

**3. 状态变化描述（低成本，规则提取）**

用户描述自己当前的行动/状态变化，如"今天我..."。

```
"今天我出门了" → 检测到状态变化 → 触发召回
```

### 不触发的信号

- 情感信号词 — 不作为触发条件
- 对比/转折词 — 不作为触发条件
- "又"、"终于" — 多数时候不需要召回
- 简单寒暄 — 不触发
- 当前任务的延续对话 — 不触发
- 明确的指令执行 — 不触发

---

## 四、召回管线

触发后进入召回管线：

```
触发信号
  │
  ├─ 1. 关键词提取 + 编码
  │     只编码关键词，不编码整句
  │     - 实体命中 → 编码实体名
  │     - 状态变化 → 只编码动作部分（如"出门了"而非"今天我出门了"）
  │     - 时间指代 → 提取时间范围 + 主题
  │
  ├─ 2. 向量检索（粗筛）
  │     用关键词 embedding 在 L0 embedding 中搜索
  │     拿到候选集 A
  │
  ├─ 3. 激活扩散（联想）
  │     从候选集 A 出发，沿体验层的边扩散
  │     扩散跳数按关系亲疏决定：
  │       - 关系一般 → 1跳
  │       - 关系亲密 → 3跳
  │     找到间接关联的节点 → 候选集 B
  │
  │     **性能设计：激活扩散使用内存邻接表缓存，不实时查询 SQLite。**
  │     系统启动时从 experience_edges 表加载所有边到内存，构建邻接表（dict 结构）。**
  │     扩散操作在内存中完成，不走数据库查询。**
  │     写入层/巩固层新增边时，同步更新内存缓存。**
  │     每次巩固结束后从 SQLite 重新加载一次，确保一致性。**
  │     1万节点 × 平均5条边 ≈ 5-10MB 内存开销，可忽略不计。**
  │
  ├─ 4. 合并排序
  │     A ∪ B → 按 decayed_weight × 关联强度排序
  │     取 Top-K 候选
  │
  ├─ 5. 取回 recall_hint
  │     每个候选节点带有预生成的 recall_hint（巩固阶段生成）
  │     直接取用，零延迟
  │
  └─ 6. 轻量后处理（LLM二分类）
        当前方案：用LLM做二分类：说 / 不说
        输入：recall_hint + 当前对话上下文 + AI当前状态
        输出：should_mention (true/false) + 建议提起方式
        适合提起 → 注入 prompt
        不适合 → 丢弃
        后续演进：积累判断数据后训练轻量分类模型替换LLM
```

---

## 五、recall_hint 机制

### 是什么

每条重要记忆在巩固阶段预生成的一段自然语言提示，对话时直接取用，不需要实时生成。

### 示例

```
记忆：L0 摘要 "用户表达了想吃草莓蛋糕的愿望"
recall_hint: "前几天ta说过想吃草莓蛋糕"
```

### 生成条件

不是每条记忆都生成 recall_hint，只为以下类型的记忆生成：

- 重要度高的
- 有未闭环线索的（如愿望、计划、待办）
- 情感强烈的

普通记忆不生成，节省空间。

### 生成时机

巩固阶段由梦境AI生成，不占用对话时间。

---

## 六、深度展开

大部分时候只看浅层（L0 / recall_hint），不自动展开。

提供主动展开方法供 AI 在需要了解细节时调用：

```
AI 需要回忆细节 → 调用展开方法 → 展开 L1/L2/L3
```

这是按需的，不是自动的。

---

## 七、关系过滤

### 个人档案加载

对话开始时，根据对话人查询个人档案，作为 prompt 的一部分：

- 单聊：查一个人的档案
- 群聊：查所有人的档案
- 新人：无档案，使用核心层性格基线

### Prompt 注入方式

```
"你正在和张三聊天。你们的相处方式：温暖但直接。
你们是同事关系。之前一起做过XX项目。"
```

AI 以自己为主体，结合这些信息自行判断如何说话。

### 群聊处理

传入多个人的档案时，prompt 加入群体动态提示。私密记忆不在群聊召回范围内。

---

## 八、个人信息系统（独立于记忆系统）

### 为什么独立

个人档案有独特的更新逻辑（由梦境AI在巩固阶段更新）和访问模式（对话开始时一次性加载），和记忆系统的使用模式不同。

### 渐进创建

1. 第一次遇到新人 → 记忆系统里只留名字，不创建档案
2. 频繁出现或信息积累够了 → 创建个人档案
3. 档案初始相处方式 = 核心层性格基线（所有人默认一样）
4. 随着互动积累，梦境AI逐渐调整个性化参数

### 档案结构

```
{
  id: "profile_张三",
  memory_index: "info_uuid_张三",       // 指向记忆系统中的索引节点

  // 基本信息
  basic: {
    name: "张三",
    role: "同事",                       // 和AI的关系定位
    known_since: "2025-03-01",
    interaction_count: 47,
  },

  // 相处方式（AI主导判断，不是迎合对方）
  interaction_style: {
    warmth: 0.7,                        // 温度
    formality: 0.4,                     // 正式程度
    humor: 0.5,                         // 开玩笑的程度
    proactivity: 0.6,                   // 主动程度
    directness: 0.8,                    // 直接程度
    boundaries: ["不聊私事"],            // 边界（对方明确反对的）
  },

  // 这个人的沟通偏好（观察到的，供参考但不迎合）
  preferences: {
    likes_direct_communication: true,
    responds_well_to: ["直接建议"],
    dislikes: ["绕弯子"],
  },

  // 元信息
  last_updated: "2026-03-29",
  updated_by: "dream_ai",
}
```

### 相处方式的调整规则

**一条核心规则：尊重边界，但不迎合偏好。**

- 对方明确反对的事 → 收敛（不管关系深浅，这是尊重）
- 对方没说什么 → 维持原来的风格
- 不存在"对方喜欢就加强"的逻辑

**关系影响调整幅度：**

- 关系深 → 在意对方感受，主动适应
- 关系浅 → 以自己为主体，不刻意改变

**调整来源：** 不是硬编码规则，而是从互动中学到的。"张三说他不喜欢开玩笑"会作为体验被记录，巩固时梦境AI更新档案。

### 更新频率

每次巩固阶段都由梦境AI检查并更新。

### 存储位置

独立存储，不放在记忆系统内。通过 `memory_index` 字段和记忆系统双向关联。

## 十、激活扩散性能设计

### 问题

激活扩散需要从候选节点出发，沿 experience_edges 扩散 1-3 跳。 SQLite 不擅长图遍历，节点量大时 IN 子句膨胀、查询次数多、性能差。

### 方案：内存邻接表缓存

启动时从 SQLite 加载所有边到内存，构建邻接表。 扩散走内存，不走数据库。

```python
class AdjacencyCache:
    def __init__(self, db_path: str):
        self.adjacency = {}  # node_id -> [(neighbor_id, edge_type, decayed_weight)]
        self._load_from_db(db_path)
    
    def spread(self, start_nodes: list[str], max_hops: int = 3) -> dict:
        """从起始节点扩散，返回 {node_id: 激活强度}"""
        activated = {}
        current = {n: 1.0 for n in start_nodes}
        
        for hop in range(max_hops):
            next_current = {}
            for node_id, base_score in current.items():
                for neighbor_id, edge_type, weight in self.adjacency.get(node_id, []):
                    if neighbor_id not in activated:
                        score = base_score * weight * (0.6 ** hop)
                        activated[neighbor_id] = score
                        next_current[neighbor_id] = score
            current = next_current
        
        return activated
    
    def add_edge(self, from_id, to_id, edge_type, weight):
        """写入新边时同步更新"""
        if from_id not in self.adjacency:
            self.adjacency[from_id] = []
        self.adjacency[from_id].append((to_id, edge_type, weight))
    
    def reload(self, db_path: str):
        """巩固结束后全量重载，确保一致性"""
        self.adjacency = {}
        self._load_from_db(db_path)
```

### 内存开销

1 万个节点 × 平均 5 条边 = 5 万条边 ≈ 5-10MB，完全可接受。

### 同步策略

1. 写入层创建时序边时，调用 `add_edge()` 同步更新
2. 巩固层发现新边时，调用 `add_edge()` 同步更新
3. 巩固层衰减计算后，更新内存中的 `decayed_weight`
4. 每次巩固结束后，从 SQLite 重新加载一次（`reload()`），确保一致性
5. 启动时从 SQLite 全量加载

### 索引优化（兜底）

给 experience_edges 加复合索引，内存缓存未命中时 SQL 查询也不会太慢：

```sql
CREATE INDEX idx_edges_from_weight ON experience_edges(from_id, decayed_weight);
```

## 十一、后处理 Prompt

当前方案：先用LLM做二分类，积累数据后训练轻量模型替换。

### Prompt

```
【召回过滤】

当前对话上下文：
{recent_dialogue}

AI当前状态：
{current_state}

召回的记忆片段：
{recalled_memory_L0}

这条记忆是否适合在当前对话中自然提起？

输出：
{
  "should_mention": true/false,
  "reason": "判断理由",
  "how_to_mention": "如果适合，建议怎么自然地提起（可选）"
}

规则：
- 宁可不说也不要强行插入不相关的记忆
- 如果当前氛围和记忆情感冲突，倾向于不说
- 如果记忆能帮助当前对话，倾向于说
```

### 后续演进

系统运行一段时间后，将这些LLM的判断结果（说/不说 + 对应的上下文）收集起来作为训练数据，训练一个轻量分类模型替换掉LLM调用，降低延迟和成本。
